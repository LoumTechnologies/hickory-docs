# Continuity: provenance across versions of a document

*Status: design of record for cross-version provenance. Adopted 2026-08-23 and
revised twice the same day. The first draft made element ids the primary
mechanism; the second demoted them to a fallback; **this one removes them
entirely.** What is left is a recorded correspondence, a guess where nothing
recorded one, and replay. Nothing here is built. It closes the open edge
`expression-and-log.md` left, and amends `three-provenances.md` with a fourth
family that is off by default. It depends on nothing unbuilt: continuity walks
document versions in git, which already happens in ordinary use.*

`hick lineage` answers *which span produced these bytes* exactly, and only for
the document as it stands. Blame back to an older commit lands in that commit's
document, and nothing relates that document's spans to today's. For a product
whose subject is provenance, *no worse than git* is a low bar to be sitting on.

## Addressing is solved; correlating is the gap

**Addressing** — *point me at those bytes* — is `(commit, path, line)`:
content-addressed, immutable, universally understood, free. For published
history this is the reference and nothing improves on it. Below the publication
floor it is stable forever; **above the floor it is not**, because re-emitting
the frontier mints new hashes every time (`expression-and-log.md`), and above
the floor is where the active work is.

**Correlating** — *is this span the same thing as that one?* — is what an
address cannot do. `abc123:main.rs:42` and `def456:main.rs:87` are two
addresses; neither says they are one span at two times.

Git derives a weak correlation from addresses alone — `blame` and `log -L`, with
heuristic move detection — and it is usually enough. There is one case where it
is not, and this product creates it deliberately:

> **Refactor mode is a machine for destroying textual continuity while
> guaranteeing semantic identity.** Pin a baseline, restructure the document,
> and `compare_outputs` proves the generated bytes unchanged. Blame afterwards
> says every line is new. The tool ships a feature whose purpose is *nothing
> changed*, and line-based correlation reports that everything did.

## Replay, which needs no new data model at all

Each commit contains its document, a weave is deterministic, and weave-only
checks are already affordable (`/render` and the refactor badge never execute).
So exact lineage is **recomputable at any commit**: check out, weave, map.

That is a **time slider on the lineage view**, it is the first thing to build,
and it may well prove the rest unnecessary. What it cannot do is relate two
versions to each other — it gives the state *at* a commit, never the thread
between commits.

**One limit, stated rather than discovered:** replay weaves an old document with
today's binary, so it asks for a grammar-compatibility promise the product has
not made — `pre-launch.md` reserves the right to break the grammar, and says
document formats deserve more care than code precisely because a `.hick` file
outlives any version of the tool. The honest claim is *replay works back to the
last grammar change*, and the slider says so at the boundary rather than failing
obscurely.

## Recorded correspondence: the mechanism

The case that motivated all of this hands you the answer for free.

**Refactor mode proves the outputs are byte-identical, which makes the outputs a
join key.** An output byte maps through lineage to a span in the baseline
document *and* to a span in the restructured one. Compose, and the old-span →
new-span correspondence is exact, derived at that moment, with no identity
scheme involved. The extension needed is small: `RefactorBaseline` stores only
output contents today, and must also pin the baseline document text, from which
lineage is recomputable.

The same shape holds wherever the tool holds both sides at once:

| Where | What is in hand | Precision |
|---|---|---|
| Refactor mode | baseline document + outputs, proven identical | **byte** — joined through the outputs |
| The up-loop / the app | `WovenState` remembers the exact bytes it wrote | byte, for the spans it mapped |
| **A merge** | base, ours, *and* theirs | the richest available anywhere |
| **A re-scaffold** | the ingested bytes, the fresh run, and the document's edits | three-sided, at diff precision |
| Pre-commit repair | HEAD's document and the working tree's | line, by matching |

The re-scaffold row is the one that is not obvious, and
`owning-what-a-scaffolder-wrote.md` is where it comes from: a scaffolder's
output, once ingested, is document bytes with a recorded source hash, so running
`dotnet new` again holds all three sides at once. It is also the case that
forces a distinction the two categories below would otherwise hide. **A
correspondence can be coarse because nothing was watching, or because nothing
exact exists to record** — two runs of a scaffolder share no history, so there
is no byte-precise thread even with the tool watching the whole time. The first
is a gap in coverage and the second is a property of the artifact; only the
first is worth adding a hook for.

**Recorded correspondences compose exactly.** Fifty hops of exact
correspondence is still exact, unlike matching done fresh at query time, which
decays multiplicatively. That is the whole reason to record at the moment rather
than infer later.

**Precision is a property of the recording site, not of an anchor scheme.** Each
correspondence carries the precision it was recorded at, and a query that
composes several reports the weakest link in the chain. That replaces the
layered-anchor design of the previous draft: there is nothing to layer, because
each hop already knows how well it was captured.

## When nothing was watching

An edit that escapes every recording site — no watch, no merge driver, no hook —
has no exact thread. Rather than carrying an identity scheme through every
document forever to insure against it, the answer is:

1. **Ask an agent to guess.** *Which element became which* is semantic matching,
   exactly where similarity heuristics are weakest and a model is strongest.
2. **A person confirms it**, and it is recorded as a correspondence marked
   **asserted, reviewed** — a declared claim, which the product already knows
   how to represent and draw.
3. **Or shrug**, and add the hook so it does not happen again. The failure mode
   was never wrongness, only coarseness.

**Why no ids.** An earlier draft minted UUIDv7 ids into documents so a span kept
its identity through an unwatched restructure. Removing them deletes the
minting triggers, the duplicate lint, the anchor grammar, the encoding question,
and the ids themselves out of every document — which keeps `bare-documents.md`'s
promise that a note looks like a note. It also makes the model *more* honest:
an id is bytes anyone can edit or paste onto an unrelated element, so a link
that looked derived was forgeable. With ids gone, every link is one of two clean
things — **a recorded fact, or an explicit guess** — and the uncomfortable
middle disappears.

## Two artifacts, and neither is a cache

| | Kind | Committed? | Can CI use it |
|---|---|---|---|
| **Correspondence journal** | a **record** — captures what happened, not recomputable later | **the project's choice** | only if committed |
| **Sessions** | a record | gitignored by default | only if committed |

The previous draft also proposed a continuity *index*. It is gone: its main
content was which ids appear in which commit, and its remaining job — the
output-to-span map — is what replay recomputes on demand, one commit at a time,
weave-only, while a person waits. So there is no cache here at all, and with it
goes the whole question of state that could be believed over the repository.

A journal is not derived state: it exists precisely because what it holds cannot
be recomputed once both sides are gone. Records belong in git if you want them,
so whether CI can check anything here is a line in `.gitignore` rather than a
property of the design. `hick init` writes `sessions/` and `.hick-cache/` today;
the journal path would be one more default a project can delete.

**Sessions in a cloud: yes, if it is the user's own.** A private repo they push
to is fine and already possible — remove the `sessions/` line and commit them.
What stays out of scope by decision rather than by sequencing is a session store
*we* run (`local-only.md`). The distinction is `notes-ide.md`'s: nothing talks to
a server we run, which is not the same sentence as nothing leaves your machine.

## The repair, on the same switch as the ribbon

At commit time both sides are in hand — HEAD's document and the working tree's —
which is the same position `refactor/end` is in. So the pre-commit hook does not
reject an unwatched edit; it reconstructs the correspondence and records it.

> **An unwatched edit leaves its correspondence behind before it is committed.**

Two rungs, honestly labelled: recorded at edit time (byte-precise), or
reconstructed at commit time (line-precise, but recorded **once**, so it does
not decay across later hops).

**And the whole of it rides one switch.** An earlier draft made the overlay
opt-in and the coverage check mandatory, which was incoherent — it taxed every
commit to feed a feature most people never turn on, and taxed hardest the
workflow the product is built around, since editing generated files in your own
editor is by definition unwatched. **No continuity, no journal, no check.** Turn
it on and you opt into the ribbon and the bookkeeping together.

That the check *is* the repair is what makes this safe: there is no enforcement
mode to reason about, and a rule with no escape hatch gets the hook disabled
entirely, taking the `hick test` gate down with it. The message says what it
recorded, not what it refused.

**Where the invariant genuinely breaks**, written as scope rather than
discovered: **merges**, addressed below; **your other machines**, since a journal
on the Windows box is not on the laptop (`one-engineer-many-machines.md`); and
**the phone**, which edits and syncs by git with no loop watching. So the promise
is *edits you author locally* — never *continuity is always exact*, which would
be believed.

**Pre-commit is stricter than CI here, and that is not a parity violation.**
`pre-commit-ci-parity` forbids passing a hook and then failing CI; this is the
other direction. But the rule has different strength in the two places, which is
worth writing down.

## Merging is the richest recording site there is

A merge is the one moment when **all three versions are in hand** — base, ours,
theirs. Richer than a watched edit (one before, one after) and richer than the
pre-commit repair (two sides). Merging through the tool does not merely avoid
punching a hole in continuity; it produces the strongest correspondence
available anywhere in the system.

The machinery is largely present: `hick-merge` does three-way merge over
documents, and `apps/web/src/lib/merge.ts` already does three-way in the editor
for drafts. **A merge tab is surfacing it**, and it is where a conflict
resolution can be recorded as it is made.

**Make it automatic rather than a team rule.** `hick-merge` registered as a git
merge driver means `git merge` on the command line runs the same code as the tab
— one path, no discipline required — with `hick init` writing `*.hick merge=hick`
into `.gitattributes`.

One sharp edge, of the kind this product refuses elsewhere: **the driver
definition lives in `.git/config`, not in the repository**, because it is an
executable command and git will not let a clone hand you one. So every clone must
run `hick init`, and **an undefined driver makes git silently fall back to the
default line merge**. The pre-commit hook checks the driver is configured and
says so, rather than letting a teammate's merge quietly produce an unwatched
document.

**But the hook cannot be the only check, because `hick init` installs the
hook.** A clone that never ran it has neither the driver nor the thing that
would report the driver missing — which is precisely the clone the check exists
for. So the configured-driver check belongs somewhere that runs without having
been installed: at project open in the app, and in `hick test`. That is the same
onboarding step `the-merged-view.md` names for a fresh clone's local fact set,
and the two should be reported together rather than discovered separately.

**Rebase-instead-of-merge does not buy this.** A rebase replays commits, replayed
commits conflict, and resolving a rebase conflict writes text nobody typed — same
hole, same size. Rebase buys linear history, which is a fine thing to want for
other reasons. The axis that matters is **who resolves the conflict** — the tool,
or a person in a text editor with `<<<<<<<` markers — and a team rule written
about *that* holds under either workflow.

## The fourth family, off by default

Continuity answers a different question from the other three: they say *why is
this here* about the present, and it says **what was this before**.

| | What it says | Forgeable? | Drawn |
|---|---|---|---|
| Lineage | these bytes came from that span | no | solid, lineage palette |
| Context | this was in front of the model | no | dotted, amber |
| Declared | the author says it rests on those | yes | dashed, grey |
| **Continuity** | this span and that one, at an earlier commit, are the same thing | **no, where recorded** | its own hue, **only when enabled** |

Two properties worth stating:

- **Every link is a recorded fact or an explicit guess**, and says which — along
  with the precision it was captured at. Removing ids is what made this clean:
  there is no longer a link that is derived-but-forgeable. A guess is drawn in
  the declared family's language, because that is what it is.
- **It is a setting, off by default.** `three-provenances.md`'s thesis is that a
  reader must tell the families apart at a glance, and a fourth stroke taxes
  everyone, including people who never ask a history question. It sits beside
  the existing toggles as per-user UI state in `hickory-workspace` rather than a
  `HICKORY_` variable, because it is a preference and not machine
  configuration.

## Sequence

1. **Replay** — the time slider, exact lineage at any commit, with the grammar
   boundary stated. No new data model, and it may prove the rest unnecessary.
2. **Recorded correspondence in refactor mode** — pin the baseline document
   alongside its outputs, join through the unchanged outputs, write the journal.
   The highest value per line of code here.
3. **The merge driver and the merge tab**, with the configured-driver check.
   This is where the largest hole is.
4. **The repair** in the pre-commit hook, on the same switch as the ribbon.
5. **The agent guess**, with human confirmation, recorded as asserted.
6. **The overlay**, last — and only if the query turns out to want drawing on top
   of the present document.

## Open edges

- **Replay couples history to parser stability**, and `pre-launch.md` reserves
  the right to break the grammar. Stating the boundary is enough now; it stops
  being enough the first time someone wants to replay across one.
- **Above the floor, the journal's keys churn.** `(commit, path, line)` is
  stable below the publication floor and not above it, because re-emitting the
  frontier rebuilds commits rather than patching them
  (`expression-and-log.md`) — and above the floor is where the active work is.
  A journal keyed on those addresses is invalidated wholesale by one
  re-emission, and because it is a record rather than a cache it cannot be
  rebuilt. The same is true of a pre-commit repair recorded against a commit
  that re-emission then replaces. Three exits and none is chosen here: entries
  above the floor are provisional and get rewritten alongside the commits they
  name, which concedes that part of the journal is derived after all; or
  correspondences are keyed by the content hash of the spans rather than by
  commit address, which is also what the next edge wants and is suspicious for
  exactly that reason; or the journal records only below the floor, and the
  frontier gets replay and nothing else.
- **Journals across machines.** Committing the journal makes it shareable and
  makes it a merge target — a record of correspondences that itself needs
  merging. Append-only keyed by content hash is the obvious shape and is not
  designed here.
- **A deleted element** is where the thread genuinely ends, and it is exactly the
  case where someone most wants to know what happened. Replay answers it; the
  correspondence chain does not.
- **The agent guess costs tokens on a machine that may have no key.** Everything
  else here is offline. That is a real asymmetry with the rest of the product,
  and the degradation — no key, no guess, coarser answer — needs to read as a
  limit rather than a failure.
