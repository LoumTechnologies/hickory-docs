# The Document Toolbar Uses Words An IDE User Already Knows

Given a document open in the app, when its toolbar is read by somebody who has
used a traditional IDE, then every control means what that word means
everywhere else: **Run** is the primary action, **Test** is what `hick test`
does, and nothing on the strip is a word another editor has already given a
different meaning to. A document-wide action that is real but rare lives in an
overflow menu, named by what it produces.

The status bar's problem count **opens a list**. Clicking it shows every error
and warning across open documents, worst first, each row naming the file and
line and jumping there when picked. **F8** goes to the next problem, which is
what the click used to do alone.

## Why

The toolbar read `Run · Verify · Refactor`, with `Verify` as the primary, and
two of those three were wrong for the audience most likely to be reading them.

- **Verify** is our word for what the CLI calls `hick test`. Matching the
  command is worth more than a word of our own: somebody who reads the toolbar
  can then type the command, and somebody who reads the command can find the
  button.
- **Refactor** named a *mode* — pin the woven outputs, restructure, be told
  the moment a generated byte would move. In every other editor that word
  opens a menu of rename / extract / inline, so the label promised a code
  action and delivered a session. It is now `Pin outputs as a baseline` in the
  overflow menu, named for what it produces, and the toolbar shows the verdict
  only once there is one to show.
- **Run** was not the primary and should always have been: it is what a person
  presses fifty times a day.

The problem count had the opposite failure — the right verb, unreachable.
Clicking jumped to the next diagnostic *in the focused document*, so a count
that included another pane's diagnostics could be clicked with nothing
happening at all, and there was no way to find out what the three problems
were. A count you cannot expand is a number with no way in.

  are present, `Verify` and `Refactor` are **absent** (a regression here is a
  word creeping back), the menu carries the baseline item, and both buttons
  disable during a run. `apps/web/src/components/ProblemsPanel.test.tsx` —
  worst-first ordering, hints excluded to match the count, the row's file:line
  is one-based, and an empty list says so.
- The count and the list read the **same** source — `registry.all()`'s
  `lspDiagnostics` — so a number in the status bar and the rows behind it can
  never disagree. That was already true of the count; it is what the old jump
  did not honour, since it looked only at the focused document.
- Caveat requiring LLM review: neither the count nor the list sees a
  **generated-file** pane's diagnostics — those panes hold their own LSP and
  are not in the registry. Nothing regressed here, but "3 problems" means
  three in the open documents, not three in the project.
