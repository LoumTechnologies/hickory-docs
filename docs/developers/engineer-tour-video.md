# Record the meeting-to-verification walkthrough

Start in an ordinary project. Open **AI engineer tour** and choose **Create and
open an isolated practice repository**. Show the new path/window and its Git
history. The meeting, mistaken proposal and initial author are transparent fixtures;
subsequent product actions produce real evidence. The original project stays open.

1. Import the seeded VTT using the tour's normal-import action. Open its retained
   original and cite the utterance carrying “including retries.” Inspect R1 in
   `deadline-spec.md`. Audio recording is optional; do not imply the VTT came from
   a live microphone.
2. Enable author colors in Lineage settings. Identify the fixture-generator Git
   credit as generated seed provenance, not authenticated human authorship.
   Select the exact “The deadline bounds…” claim and create a real review thread
   explaining the missed qualification.
3. In the tour's shared debugger, bind a source breakpoint and run. Expand source
   observations to show **PAUSED HERE**, the bound marker, scoped values, evidence
   IDs and action/location handles. Pin the observations. Continue execution and
   observe the specific 160ms-versus-100ms failure. Historical browsing is not
   reverse execution; this browser backend does not support reverse/restart-frame.
4. Close the tour without resetting it. Open `deadline-spec.md` and `AGENTS.md` in
   the real workspace. In the workspace agent, explicitly ask it to read both.
   Add “including retries” to the instruction file, inspect Changed agent context,
   and queue its selected patch. Send a subsequent message and inspect the actual
   included-request receipt. Keep instruction role/scope as actually supplied.
   The tour also checks that the paused/breakpoint IDs were in confirmed context.
5. Through the actual review thread, send an investigation to the workspace
   conversation. This is a real configured model request and may cost money;
   show the provider before pressing Send. Inspect the actual response/session and
   focused diff. Approve the correction through the existing edit-review controls.
6. Refresh observed evidence and run native verification. Show the run ID,
   current-source hash and execution-cell results. If generated output is behind,
   weave the document through the normal engine/terminal before retrying. The
   independent stdout expectation checks total allocation, short attempts and an
   empty sequence; it does not establish real network or OS timing.
7. Open `hotspot.md`. Use Runtime observations with `hotspot.py` and cProfile.
   Expand the actual `subtotal` hotspot and pin its evidence in next context.
   Explicitly send that selected context to the workspace agent. Replace the loop
   with the arithmetic formula through reviewed edits. Rerun correctness and
   profiling. Compare separate run/source IDs, call counts and timing scope;
   disclose profiler overhead and do not promise a fixed speedup. The gate needs
   two completed source revisions and a confirmed receipt containing an actual
   profile event ID.
8. Inspect the correction, runtime logs/emitter navigation, verification and
   profiling comparison. Resolve the actual review thread yourself. A passing
   check and a model's response never resolve it automatically.
9. Open the published-results index, download a result and load its JSON in the
   tour. Compare source/dependency identity and the tested Git revision. Different
   source bytes stay stale: publish that reviewed version through the existing
   allowlist/CI path rather than forcing a match or relabeling old success.

Close/skip preserves the phase and mounted pinned evidence; restart clears local
execution witnesses and meeting/publication selections, without deleting the
practice repository or historical product records. A fresh browser reload retains
the phase but requires execution witnesses to be established again. Refresh reads
actual review, runtime and delivery records rather than trusting button clicks.

For recovery, retain the visible error and retry the same bounded action. Missing
provider configuration, sandbox/Node/Python dependencies or publication evidence
remain unavailable. Do not advance by substituting example responses. A browser
host without native window powers receives the created path and an explanation;
open it in a separate Hickory window manually.

Before calling the demo launch-ready, record the whole native-window/provider
path and verify the deployed homepage's **Build source** link against the released
commit. The homepage's own JavaScript run is live; proposals/corrections are
recorded examples, and native capture/profiling/model calls are desktop actions.
This session has not established full native-window or deployed-revision readiness.

Check detached regressions yourself with `just checks-status` and
[GitHub Actions](https://github.com/LoumTechnologies/hickory-docs/actions).
