# Audience First Literate Docs

Write for a maintainer learning or changing one stakeholder-visible behavior.
Explain the behavior, show the code that implements it, and show how its important
outcomes are checked, in a useful reading order.

## Index shared source through useful readings

Treat a literate view as an explained index into actual source: organize the code
and its tests around a reader's questions, decisions and change path. Show exact
maintained fragments beside the reasoning, with provenance back to their source.
A file list or symbol catalog alone is not a literate index.

The same implementation can support several readings: a construction tutorial
for a newcomer, a request-path reading for a maintainer, or a failure-boundary
reading for a reviewer. Let audiences change explanations, selection and reading
order without creating independently maintained copies of code. One source owner
does not mean one narrative view. Reuse supported source slices, fragment
references or includes; do not retype code to give each audience its own version.

Before creating a view, inspect existing readings and identify the audience and
concrete task it will serve. Extend a suitable view when possible. Add a reusable
view when repeated investigation or maintenance is likely—for example, following
an authorization path across several files or repeatedly locating the same safety
checks. A first investigation can justify a view when the task will clearly recur;
do not wait for an arbitrary repetition count. Keep one-off notes lightweight
and avoid a view for every file, symbol or hypothetical audience.

Give a reusable view a discoverable name, a short audience/task statement, and
links or provenance to the source and relevant tests. Add it to the project's
existing reading index, or keep it through the tool's view library when that is
the supported persistence model. State which files or behavior it covers and any
unexplained remainder; a selected-source reading is not whole-project coverage.
Do not add a separate registry when existing navigation provides discovery.

## Teach construction when that is the reader's task

For a construction tutorial, begin with
a short thesis about what we will build, create the initial scaffold or files,
and develop the implementation in a sequence the reader can follow.

For each substantive step, establish what we have so far, introduce the next
concrete need, explain the choice, add the actual maintained code or patch, and
show the assertion or runnable checkpoint that demonstrates the result. Reveal
requirements when they motivate a decision; keep product review indexes secondary.
Use active construction language such as “we need to retain the output's file
kind, so add it to the entry” rather than “this module handles metadata.”

The tutorial must present real implementation and tests through maintained
constructions or exact source-backed views. Links, includes and chapter headings
can connect the story, but cannot substitute for interleaving reasoning with the
code the reader is learning to construct. Move fragment ownership only when the
maintained construction needs it; another reading need not change ownership. Preserve exact generated bytes during a prose
or organization change. A tutorial may explain the final design in a teaching
order without inventing historical commits or claiming incomplete stages build.

Keep scaffold captures inline and folded by default; explain authored patches
above that immutable base. A small project must still be expressible in one
Markdown document. Aim for balanced explanation and code in typical implementation
steps without imposing a numeric quota on tests, assets, scaffolds or navigation.

## The unit is an explained behavior

Give every substantive code fragment an owning explanation. Code without a
meaningful place in the narrative is a design or documentation smell to inspect.
Explain why the fragment exists, what decision it makes, or which invariant or
failure case it protects. A path, hash, symbol name, or generic "edit this entry"
paragraph does not provide that explanation.

Interleave at meaningful reasoning boundaries: a check, transformation, state
transition, failure path, or coherent group of declarations. Avoid a sentence per
line and a long file dump after a high-level promise. Keep small obvious plumbing
with the behavior it supports; do not manufacture prose to fill a quota.

Navigation pages and shared conceptual explanations may contain no code. Do not
split a behavior into contract, review, construction, and payload pages merely to
satisfy a template. Keep explanation, relevant implementation, and focused tests
readable together. Split when a reader's task or reusable abstraction changes,
rather than at every output-file boundary.

## Start from the reader's change

1. Identify the reader and their next concrete task. Read the current requirement,
   actual implementation, and relevant tests before explaining the behavior.
2. Trace the path from input through decision to observable result. Identify
   errors, units, state ownership, ordering, and side effects that affect the task.
3. Arrange that reasoning as explanation → actual maintained code → next
   explanation. Introduce a failure example before its refusal logic. Place an
   assertion beside the outcome it demonstrates.
4. Keep review status and evidence limits near the claim they qualify. Distinguish
   implementation inspection, executed checks, and human acceptance. An include,
   reference, test name, or passing unrelated test cannot establish correctness.

Explain the surprising part. For example: "Validate before subtracting so an
invalid request cannot become a negative balance" helps a maintainer decide
where to insert a new check; "This function validates the request" adds little.
Do not invent stakeholder guarantees from a convenient implementation detail.

## Use the project’s literate toolchain

Identify the maintained source, generated outputs, assembly mechanism and focused
verification commands before editing. Preserve the existing literate format; do
not introduce Hickory or migrate toolchains unless requested. For formats other
than Hickory, use their supported fragment and assembly equivalents. The Hickory
syntax below applies only to Hickory projects.

Inspect the project's entry document, local instructions, and supported Hickory
syntax. Use the installed implementation or its tests to resolve uncertain
semantics; do not invent assembly features or assume a Markdown fence generates
code. Respect the project's namespace binding and execution environment.

Use `copy` fragments beside their explanations and explicit `paste` selections in
a `file` construction when a file needs several explained pieces. Keep narrative
order useful to the reader and assembly order explicit for the compiler. Stable
fragment names describe responsibility, not line positions. Preserve indentation,
inter-fragment whitespace, encoding, final newlines and metadata.

Raw `entry` payloads preserve bytes, including embedded tag examples; do not
assume they expand nested `paste` tags. Check delimiter collisions when choosing a
namespace prefix. Keep exact assets and binary payloads in appropriate literal
constructions with a brief explanation of their role.

Read [the worked literate example](references/interleaved-example.md) when introducing
fragment assembly or demonstrating the intended reading experience. It constructs
a small Python implementation and its tests. It is a pattern, not a mandated
language, naming scheme, or test framework.

Within the authoritative construction, maintain one definition for each shared
fragment and one construction owner for each output. Alternate views may present
the same source through different explanations and arrangements. Explain a shared
abstraction at its owner; other readings explain it to their audience through
source-backed selections and retain provenance to that owner. Do not duplicate implementations or test bodies to
make every guarantee look self-contained. Do not assign unrelated code to a
guarantee just to remove an ownership warning.

When code lacks a clear owner, inspect its callers and purpose. Place it under an
honest behavior or shared mechanism if supported by the code. Otherwise record
the unresolved ownership and what needs inspection. Do not hide it in an
unexplained support bucket, delete it on that evidence alone, or claim the whole
codebase is explained after processing only some files.

## Check that alternate views retain the same code

Separate reading order from assembly order. When creating or rearranging a
Hickory source-backed view, use the supported exact-slice arrangement mechanism:
it covers each selected file's bytes once, assembles in source order and rejects
an arrangement whose reconstructed code differs. Do not invent view syntax or
assume ordinary Markdown links establish reconstruction equivalence.

Check every added or changed view against the same source revision and declared
file scope. Use the toolchain's deterministic reconstruction comparison; compare
paths and exact bytes, plus kinds and portable modes where supported. If views
cover different subsets, compare each against its backing files and compare
shared outputs; do not claim all views reconstruct the whole repository.
For independent Hickory documents, inspect the installed `hick equiv` interface
and its configuration limits before using it. Report the configurations actually
checked; a bounded comparison is not proof for untested configurations.

Keep code authoritative in its existing home. For ordinary source-backed Hickory
views, prose and arrangement can remain personal while code edits write through
with revision and backing-byte checks. For document-backed projects, edit the
owning constructions. After code changes, refresh affected views from current
source and review their explanations for staleness. Equality of generated code
checks reconstruction, not the truth of prose or correctness of the program.

## Preserve the maintained source

Follow the backing model: edit owning Markdown constructions in document-backed
projects, or use supported source-backed edits for ordinary source files. In a reorganizing
change, hold generated outputs fixed unless the user also authorized behavior
changes. Record the starting inventory and compare the completed reconstruction
for exact bytes, paths, kinds and portable modes. A successful build is not a
byte-equivalence check.

Update include edges, ownership maps and incoming links when moving fragments.
Retain requirement decisions and evidence dependencies; distinguish current
contracts from historical text. Consolidating pages must not silently discard an
exclusion, failure case, or unresolved verification note.

Regenerate through the project’s toolchain, then run the project's source/output and ownership
checks plus relevant focused behavior or safety witnesses. If the evaluator or
adapter changed, repeat with the rebuilt implementation. Use a fresh temporary
directory when checking Markdown-only reconstruction. Follow local limits on
tests, commits and status monitoring; this skill grants no publishing permission.

When maintaining Hickory Docs itself, read
[the repository-specific workflow](references/hickory-self-hosting.md). Its paths,
ownership records and publication rules are local conventions.

## Measure whether a view helps real work

When evaluating an index or claiming time/token savings during work driven
through Hickory, use its in-app feature measurement on an ordinary Codex ACP
implementation request. The human
opts in through **Measure this request with and without Hickory features**;
do not enable extra agent runs through an agent UI action or invent a separate
benchmark runner. A reusable view is a candidate intervention, not evidence of
improvement merely because it exists.

Read [the measurement workflow](references/feature-measurements.md) when collecting
comparisons, extending supported interventions, or reporting feature benefits.
Keep the same task and captured code across arms, preserve failures and unknown
usage, and separate completed work from independently reviewed correctness.
Record negative savings and unmeasured features as prominently as improvements.
Outside Hickory, use the chosen environment’s existing measurement facilities
when available; otherwise retain unmeasured status. Do not introduce a runner or
migrate tools merely to satisfy this skill.

## Review the result as a reader

- Can the intended maintainer follow one behavior from explanation to actual
  implementation and a meaningful assertion without a chain of wrapper pages?
- Can readers find the right view for recurring work, and trace its code back to
  the shared authoritative source?
- Do alternate views reconstruct their declared files exactly at the checked
  revision, with scope and configuration limits stated?
- Does the prose explain decisions and constraints rather than translate syntax?
- Does each substantive fragment have an honest owner, including shared code and
  tests? Are remaining ownership gaps visible and specific?
- Are the useful path and important failure paths explained, with evidence
  described only as strongly as the checks support?
- Do generated outputs agree with maintained source, and with the starting bytes
  when this was a reorganization? Are intentional differences accounted for?

Report the scope actually improved and what remains. File counts and link
coverage measure organization; they do not establish explanatory quality.
