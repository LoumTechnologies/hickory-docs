# Docker-Compose Across Multiple Worktrees

## Why this matters

The whole point of `git worktree` is running several branches of the same
repo side by side on one machine. If the dev environment picks a fixed
container name, network name, project name, or host port, two worktrees
fight over it the moment both try to run `just dev`. Nothing here should
require the developer to notice or manually resolve that — it should just
work.

## The untracked per-worktree config file

- Lives at the repo root, e.g. `.dev-env.local`. Gitignored — it is
  regenerated per checkout, never committed, never shared between
  worktrees.
- Generated the first time `just dev` runs in a worktree that doesn't have
  one yet. Simplest reliable identity: a short hash of the worktree's
  absolute path (stable across restarts of that worktree, distinct from
  every other worktree and every other repo on the machine).
- Minimal shape (adjust format to the project's config conventions — TOML,
  `.env`, whatever the rest of the repo already reads):
  ```
  # generated by `just dev` — do not edit, do not commit
  COMPOSE_PROJECT_NAME=jc-a1b2c3d4
  ```
- Every recipe that touches docker-compose reads this file (e.g. via
  `docker compose --env-file .dev-env.local` or by exporting
  `COMPOSE_PROJECT_NAME` from it before invoking compose) so containers,
  networks, and volumes for this worktree are namespaced under
  `jc-a1b2c3d4_*` and never collide with another worktree's `jc-<other>_*`.
- If the file already exists, reuse it — regenerating it on every `just
  dev` would break the "safe to kill and re-run" idempotency contract by
  orphaning the previous run's containers under a name nothing references
  anymore.

## Optional: direnv for auto-loading it

If the project uses (or wants) [direnv](https://direnv.net/), an `.envrc`
at the repo root can `source .dev-env.local` (or export its values) so the
right `COMPOSE_PROJECT_NAME`/PortZero URL is already in the shell on `cd`
into that worktree — no `just dev` needed just to inspect state. The
`.envrc` **must** start with:

```bash
source_up_if_exists
```

before anything else, so a developer's own parent-directory `.envrc` (e.g.
a personal direnv setup above their `~/src` tree) keeps loading instead of
being silently shadowed by this repo's file. This is not required — plain
shell export from a `just` recipe works fine without direnv — but if direnv
is already part of the project's or developer's workflow, wiring it in
this way is the one that composes safely with whatever else they have.

## `docker-compose.yml` itself

- No `container_name:` on any service — let compose derive
  `<project>_<service>_<n>`, which is already unique per worktree once the
  project name is.
- No host-side port literal in `ports:` (e.g. avoid `"5432:5432"`). Either
  omit the host port (`"5432"`, compose picks an ephemeral one) or bind
  explicitly to port `0` for app services that need to advertise their own
  address to PortZero.
- No hardcoded network name — the default per-project network compose
  creates is already isolated by project name.

## PortZero wiring

- Any service other code (browser, another service, a developer) needs to
  reach by a stable name registers that name with PortZero rather than
  publishing a fixed host port. `just dev` (or the service's own startup)
  does the registration; developers/docs reference the PortZero name, not
  a port number.
- For a containerized service that only other containers in the same
  compose project need to reach, PortZero isn't necessary — compose's
  internal DNS (service name) already works, and it's already
  project-scoped.

### How registration actually works

There is no API call and no config file. **Launch the process with
`PZ_TUNNEL=<domain>:80` set and have it listen on a port; the daemon detects
the pairing on its own.** The app never reads `PZ_TUNNEL` and never needs to
know what port it got:

```
PZ_TUNNEL=api.jc-a1b2c3d4.portzero.local:80
PZ_HEALTH_PATH=/health     # optional; lets `portzero wait --healthy` gate on real readiness
```

Derive the subdomain from the same per-worktree slug as the compose project
(`api.<slug>.portzero.local`, `web.<slug>.portzero.local`) so the hostname is
known *before* the service starts — that's what lets you hand a frontend its
API URL without waiting to discover a port.

Useful commands: `portzero status` (is the daemon running), `portzero url
<domain>` (script-safe, prints only the URL), `portzero wait --healthy
<domain>` (readiness gate for CI). Working minimal examples per language,
including a docker-compose variant, ship at `~/.portzero/examples` — read
those rather than guessing at the wiring.

### PortZero must be optional

The daemon won't be running in CI, and a contributor may not have installed
it. Probe once (`portzero status` exits 0 and reports a running daemon) and
fall back to OS-assigned ports, printing whatever each service reports.
Falling back is not a violation of the no-hardcoded-ports rule — an
ephemeral port that nothing writes down is still nothing written down. This
fallback is also what makes the dev-environment CI job possible at all.

### Not every server honors port 0

`listen(0)` is the ideal, but some dev servers treat `0` as "unset" and
silently substitute their own default — Vite falls back to 5173, which is
exactly the cross-worktree collision the rule exists to prevent, and it
fails *quietly*. When a server does this, pick the port yourself and pass it
in: bind a throwaway socket to port 0, read the assigned port, close it, and
hand that number to the server via env var. Still no port written down
anywhere, and it works with servers that won't do it themselves.

Verify rather than assume: start the service and check the port it reports
is not the framework's documented default.

## `dev-clean` semantics

- Reads the same untracked config file to scope `docker compose -p
  <project-name> down --volumes` (removes this worktree's containers,
  networks, and volumes) plus `docker image rm` for any image this repo's
  compose file **builds** (`build:` in the compose file), never an image it
  only **pulls** (`image: postgres:16`, etc.) — pulled images are shared
  across every worktree and repo on the machine and are expensive to
  redownload.
- Must never target another worktree's project name. If the config file is
  missing (nothing to clean), it's a no-op, not an error.

## Devcontainer (optional)

If a `devcontainer.json` is added, it should reference the same
`docker-compose.yml` (VS Code's `dockerComposeFile` + `service` +
`workspaceFolder` fields) rather than defining a second, parallel
container setup — one source of truth for the dev stack. It remains
entirely optional; nothing in this skill requires it.
