
# The Hickory Grand Tour

This is an executable document. Every number, table, chart, and file you see
below is produced by running the document itself — `hickory run` executes the
cells, weaves this markdown, and writes the generated artifacts;
`hickory check` re-executes everything and fails the build if any output has
drifted from what is committed. Nothing here is pasted in by hand.

The tour covers four things Hickory does that notebooks and static docs
don't:

1. **Literate weaving** — many prose sections assemble one runnable source
   file, with per-character lineage from the file back to the section that
   contributed each fragment.
2. **Polyglot cells** — SQL through DuckDB, with verified tabular output.
3. **Real analysis + generated interactive artifacts** — a Polars regression
   whose fitted model is baked into a self-contained HTML explorer.
4. **Feature-gated sections** — an R/ggplot chapter that only runs when you
   ask for it, so the document stays runnable on machines without R.



## 1. Literate weaving: a program in prose order

Classic literate programming: the document is written for readers, and the
machine reassembles the code in program order. Each subsection below
contributes one fragment via `h:copy`; a single `h:file` at the end pastes
them together into `analysis.py`. In the web editor's Output view you can see
`analysis.py` fully assembled — and edit it there, with per-character lineage
tracing every byte back to the section that contributed it, so edits flow
back to the right place in this prose.

### A deterministic random number generator

Reproducibility is the whole game, so the synthetic data comes from an
explicit linear congruential generator rather than any library RNG. Same
seed, same bytes, on every machine, forever:

```python

def lcg(seed):
    """Deterministic 31-bit linear congruential generator."""
    state = seed
    while True:
        state = (state * 1103515245 + 12345) % (2 ** 31)
        yield state

```



### Synthesizing the ledger

Twenty-four sales records across four regions, seeded so the report is the
same everywhere:

```python

REGIONS = ["east", "north", "south", "west"]


def make_sales(seed=2026, n=24):
    """Return `n` synthetic sales rows: (region, units, unit_price)."""
    rng = lcg(seed)
    rows = []
    for i in range(n):
        region = REGIONS[i % len(REGIONS)]
        units = 1 + next(rng) % 50
        unit_price = 10.0 + (next(rng) % 9000) / 100.0
        rows.append((region, units, round(unit_price, 2)))
    return rows

```



### The report

Aggregation and a plain-text report — the part a reader actually cares
about, so it gets its own section:

```python

def revenue_by_region(rows):
    totals = {}
    for region, units, unit_price in rows:
        totals[region] = totals.get(region, 0.0) + units * unit_price
    return dict(sorted(totals.items()))


def main():
    rows = make_sales()
    totals = revenue_by_region(rows)
    for region, revenue in totals.items():
        print(f"{region:<6} {revenue:>10.2f}")
    print(f"{'total':<6} {sum(totals.values()):>10.2f}")


if __name__ == "__main__":
    main()

```

## 2. SQL is a first-class citizen: DuckDB

Cells are shell commands, so any CLI is a "kernel". Here DuckDB builds a
table of synthetic sales (arithmetic, not `random()` — deterministic across
DuckDB versions) and persists it to a database file that later cells in the
same container reuse:

  CREATE TABLE sales AS
  SELECT
    ['north', 'south', 'east', 'west'][1 + i % 4] AS region,
    1 + (i * 37) % 50 AS units,

## 3. Python + Polars: fit a model, ship an artifact

This cell uses `uv` to conjure a pinned interpreter (CPython 3.12) with
Polars available — no environment setup, no requirements file. It generates
a seeded dataset, fits a simple linear regression with closed-form least
squares written as Polars expressions, and prints the coefficients. The
expectation is a per-line regex: the shape of the result is pinned, and
since the data is seeded the values cannot drift either (the woven output
below is checked byte-for-byte):

$ uv run --python 3.12 --with polars python3 - <<'EOF'
  import random
  
  import polars as pl
  
  random.seed(11)
  xs = [round(random.uniform(0.0, 10.0), 3) for _ in range(120)]
  ys = [round(3.2 * x + 4.5 + random.gauss(0.0, 2.0), 3) for x in xs]
  df = pl.DataFrame({"x": xs, "y": ys})
  
  dx = pl.col("x") - pl.col("x").mean()
  dy = pl.col("y") - pl.col("y").mean()
  fit = df.select(slope=(dx * dy).sum() / (dx * dx).sum())
  slope = fit["slope"][0]
  intercept = df["y"].mean() - slope * df["x"].mean()
  
  pred = df.select(r=pl.col("y") - (slope * pl.col("x") + intercept))["r"]
  ss_res = (pred * pred).sum()
  dy_all = df["y"] - df["y"].mean()
  r2 = 1.0 - ss_res / (dy_all * dy_all).sum()
  
  print(f"n         = {df.height}")
  print(f"slope     = {slope:.4f}")
  print(f"intercept = {intercept:.4f}")
  print(f"r_squared = {r2:.4f}")
  
  df.write_csv("points.csv")
  with open("coeffs.txt", "w") as f:
      f.write(f"{slope:.6f} {intercept:.6f}")
  EOF

intercept = 4.8361

### An interactive artifact, generated — not hand-written

The next cell reads the fitted coefficients and the data points back and
emits a **self-contained interactive HTML widget**: a scatter plot of the
data, the fitted line, and a slider that moves a probe along `x` while the
predicted `y` updates live. The coefficients are baked in as JS constants at
generation time — no external libraries, no network, one file you can open
from disk. It is committed next to this document as `regression-explorer.html`,
and `hickory check` regenerates it on every verification, so the widget can
never disagree with the model above:



The widget's contract is enforced one cell up: the expectation pins the
printed coefficients, and the drift check pins the generated HTML
byte-for-byte.

## 4. Feature gates: the R + ggplot chapter

Some sections have heavy dependencies. Hickory features make them opt-in
without forking the document: `h:feature` declares the flag, `h:when` gates
the content, and the CLI enables it with
`hickory run examples/grand-tour.hick --features with-r`. With the feature
off, the gated cells are filtered out before the DAG is built — nothing
runs, and the woven document says so honestly instead of pretending the
section never existed.
